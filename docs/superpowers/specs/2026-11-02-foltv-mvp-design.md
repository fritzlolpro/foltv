# foltv — дизайн MVP

Дата: 2026-11-02. Статус: на согласование.

## Зачем и почему

«Телевизор» для аниме: старый ТВ + Raspberry Pi. Программа на Rust превращает
папки с видео (в т.ч. на сетевом хранилище) в «каналы»: случайный файл из
папки играет бесконечно, по окончании — следующий случайный. Управление с
пульта. Ощущение «включил телевизор и смотрю», а не выбора файлов в менеджере.

## Цели (MVP)

- Канал = папка с видео. Конфиг — список каналов; MVP обязан работать с одним.
- Случайное воспроизведение: файл кончился → автоматически следующий случайный
  из папки канала. Кнопка «next» — то же немедленно.
- Переключение каналов с памятью позиции: при уходе с канала сохраняется
  `{файл, позиция}`, при возврате — продолжение с той же секунды (или новый
  случайный файл, если канал ещё не смотрели). В любой момент — ровно один
  процесс mpv.
- Управление: ch+/-, next, pause/play, vol+/-, mute. На dev-машине (Windows) —
  клавиатура; на RPi — ИК-пульт (GPIO-приёмник TSOP + драйвер ядра `gpio-ir` +
  `ir-keytable` → события как от клавиатуры через `/dev/input`). Arduino не нужен.
- Работает на Raspberry Pi (Linux), разработка на Windows. NAS — смонтированная
  папка (SMB/NFS в fstab), для программы это просто путь.

## Не-цели (вне MVP)

- Видеостримы как источники (задумано на будущее).
- Параллельная «трансляция» каналов в фоне.
- Web-интерфейс, REST API, база данных, GUI/OSD-меню.
- Транскодирование, загрузчики контента.

## Анти-цели

- Раздувание: никаких фич и опций «на потом», которых не просили.
- Зависимости ради пары строк кода.

## Ограничения

- Rust, edition 2024; репозиторий `foltv` уже создан (пустой main).
- mpv — внешний процесс, ставится отдельно в системе (Windows и RPi).
- Кроссплатформенность там, где реально: Windows (dev) / Linux (RPi).
  Чтение `/dev/input` — только Linux; ввод абстрагируется за общий enum Command.
- Модель RPi и способ подключения к старому ТВ (composite / HDMI-конвертер) —
  вопрос железа, не кода; проверить при деплое.

## Подходы (рассмотренные)

1. **mpv как subprocess + JSON IPC** — выбрано. Простое и стандартное:
   позиция/файл читаются как свойства (`path`, `time-pos`), управление —
   командами (`loadfile`, `pause`, `volume`). Крах mpv = перезапуск без потери
   состояния самой программы. Минус: перезапуск файла при возврате на канал —
   секунда-две чёрного экрана, признано приемлемым.
2. **libmpv, встраивание в процесс.** Нет IPC-слоя, гибче, но C-bindings,
   сложнее сборка на RPi и Windows, больше кода. Выигрыша для MVP нет — отвергнуто.
3. **Чистый mpv + Lua-скрипты, без Rust.** Состояние каналов и чтение
  `/dev/input` на Lua — больно; и хочется Rust-проект. Отвергнуто.

Решение по «каналу»: один mpv + сохраняемое состояние `{файл, позиция}` на
канал (выбрано), а не N процессов на канал — экономия памяти RPi и простота.
Семантика: канал живёт вместе с просмотром; «возврат через час» = продолжение
с сохранённой секунды, без попытки симулировать «прямой эфир».

## Как устроено (решённое в разговоре)

- Конфиг: TOML, список каналов `{имя, путь}`. Канал = любая папка из
  конфига: и «пара эпизодов», и терабайтная библиотека со сложной вложенной
  структурой. Скан папки рекурсивный, фильтр по видео-расширениям.
- Случайный выбор: не повторять предыдущий файл подряд.
- IPC: mpv с `--input-ipc-server` (Unix socket / Windows named pipe);
  событие mpv `end-file` запускает выбор следующего файла.
- Кнопки → действия над mpv через IPC; «next» = `loadfile` нового случайного
  файла (replace), брошенный файл позицией не запоминается.
- Пауза между эпизодами — ок, пара секунд пустоты.
- Старт: автопродолжение последнего канала с сохранённой позиции — включил
  «телевизор», уже что-то идёт. Громкость и mute сохраняются между запусками.
- Дорожки: всегда предпочитать японское аудио и японские субтитры, если есть
  (`alang=jpn,ja`, `slang=jpn,ja`); если японских субтитров в файле нет —
  поведение mpv по умолчанию.
- Персистентность: модель питания неизвестна (возможно питание от USB-порта
  ТВ = обрыв на середине файла), поэтому состояние пишется при каждом
  изменении (кончился файл / next / смена канала / громкость), атомарно
  (tmp + rename). Как именно выключать малину — исследовать при деплое.

## Что осталось строителю (мои решения, можно оспорить)

- Крейты: `rand`; IPC — тонкий слой поверх `interprocess` (кроссплатформенный
  named pipe / unix socket) или самописный; конфиг — `serde` + `toml`.
  Выбор — на этапе плана.
- Формат файла состояния (JSON-схема) — мой call.
- Сохранённый файл канала исчез/недоступен (NAS офлайн) → тихо перейти к
  новому случайному файлу, не падать.
- Исследовать при деплое: питание/выключение RPi, аппаратное декодирование
  (флаги mpv), физический пульт (хватит ли кнопок; недостающие — комбинации).
